## Round sp19 (PTX): a warp's global load or store goes to memory as it stands, and the lockstep fingerprint folds eight words at a time (branch `sp19-ptx`, merged with `origin/main` dad11eee)

The question: the PTX interpreter is about 2.2x slower than the SASS tier on the same program; what in `exec_ld` / `exec_st` and in the lockstep launch costs the most that can go without a change of any result, counter or error text? Measured on server3 (Zen 4), one thread, `VGPU_SASS=0`, `nvidia/rtx3060`, programs from the `tools/bench/real` corpora, Release, GCC 13.3, each side built here (A = `origin/main` dad11eee, B = A + this branch), `perf stat -e instructions:u,cycles:u`, pinned to cpu 13.

### What changed (commit aa14743f, rebased by merge)
1. `exec_ld` / `exec_st`: for a full warp of one value each (`n == 1`, 32 active lanes, power-of-two width, aligned) the addresses already in `at` go to `MemoryManager` as they are (`load_broadcast` when every lane names one address, `load_batch` otherwise; `store_strided` when the lanes are on a constant stride, `store_batch` otherwise) and the values come back into the register's row without a copy. Anything the memory manager declines has touched nothing and takes the old path, so counters, errors and memory are those of the lane loop. `VGPU_FASTPATH=0` keeps the lane loop as the reference.
2. `lockstep_fold` (the fingerprint of a block's registers, taken by the SASS, PTX and AMD lockstep launches to tell a waiting block from a computing one): input of 64 bytes or more is folded by eight independent chains of the old step; only equality of two fingerprints is looked at.

### Round sp19 (PTX), part 2: the interpreter's bank passes are remembered by warp shape (`PtxBankMemo`)
`ptx_bank_passes` had no table in the PTX path and cost 14.8% of lud's and 6.5% of hotspot's cycles. The SASS tier has had `BankMemo` since sp21; the interpreter now has the same idea in `include/vgpu/exec/mem_counters.hpp` (`ptx_bank_passes_closed` / `ptx_bank_passes_open` / `ptx_bank_passes_memoized`, `PtxBankMemo`), wired in `Interpreter::count_addresses`.
* Key: as `sass_bank_passes_memo` (each active lane's address less the first active lane's word, an idle lane taken at that word, and the access width `span`), so a hit returns exactly what the counting of the words returns. The interpreter's words are `(address + 4k) / 4`, so a move of every address by whole words moves the banks together and keeps equal words equal. There is no check for the top of the address space (the SASS table has one): the move is a bijection of the words modulo 2^64, which is also how the interpreter's addition wraps, and `tests/unit/test_bank_memo.cpp` has a wrap test (a warp moved to wrap around, against the definition).
* Different from the SASS table on purpose: 128 entries of 64-bit keys (a wavefront kernel asks for a hundred shapes and more) and the mask in the hash (a partial warp has only some lanes among the eight sampled). The closed forms (a warp on a stride) run first, in `ptx_bank_passes_closed`, which is the only caller of the progression code, so the compiler keeps it in line in `count_addresses`; the table, and the host thread's table made on first use, are out of line. A first version with the table's call inside `ptx_bank_passes_memo` cost needle 2.3% to 3.3% more instructions (the progression was no longer in line, and all of needle's 3.1 M shared accesses are on a stride: the table is never reached); the split brought it to 1.0008. `VGPU_FASTCOUNT=0` still takes the reference.
* Same bits: the outputs and the per-launch counter file (`VGPU_COUNTERS_FILE`, pid dropped) of branch-without-memo and branch-with-memo hash **identical** for lud, hotspot, needle, backprop, SYRK, ATAX, GEMVER, 3MM, gaussian, pathfinder and radixsort2 (`VGPU_SASS=0`, `nvidia/rtx3060`; srad_v2 launched nothing in this setup and says nothing).
* Numbers (server3, Zen 4, cpu 13, `VGPU_SASS=0`, one thread, A = `62fb7253` (sp19-ptx before the memo), B = A + the memo, alternating 15 pairs, three fresh library copies a side, Mann-Whitney p):

## Round sp24: AMD LDS byte and halfword accesses in the tier (branch `sp24-lds`, base origin/main dad11eee)

**Profile first** (server3, Zen 4, one host thread, `perf record -e cycles:u`, simulated MI300X, rocBLAS 5.1 / ROCm 7.1 `rocblas_gemm_ex` on a 1024 x 1024 x 1024 problem, the library's own gfx942 kernels; the driver is a 60-line program that `dlopen`s `libamdhip64` and `librocblas`, checks four columns of C against a host sum, and is not in the repo). f16 in, f32 compute (HHS): `Machine::lds_access` 29.8%, `Machine::lds_fast` 15.5%, `write_half_load` 4.7%, `set_word` 3.5%, `OpName::operator==` 2.3%: 56% of the cycles in the LDS access path of the interpreter, not the 36 to 40% of the earlier profile. `VGPU_AMD_TIER_STATS=1` says which instructions the tier handed to the interpreter (n = 512): `ds_read_u16` 65,536 and `ds_read_u16_d16_hi` 65,536 of the 216,064 (61%; the rest `v_mfma_*` 32,768, `buffer_load_dword` 32,768, ...) for HHS and bf16 (BBS), `ds_write_b16` 32,768 of 134,144 (HHH, f16 compute). The kernels read the two halves of a packed operand with two halfword reads a lane. The 32-bit and wider forms (`ds_read_b32/b64/b128`, `ds_write_*`, `read2`/`write2`) were already tier handlers (sp5, sp12); the byte and halfword forms never were, and each went through `lds_access` (name facts, a `Half` built, the ladder) and `lds_fast` (a `switch` on the op in every lane) or, for the `_d16` forms, the ladder's half path with `write_half_load` and `set_word` in every lane. There is no bank-conflict model in the AMD engine (the LDS instruction counts are the only counters), so nothing of that kind changes.

### What changed
`gcn_tier.cpp`: `h_dsn` (`TIER_DUAL`, a handler of its own so the word forms' codegen is not touched), for `ds_read_u8/i8/u16/i16`, `ds_read_u8/i8/u16_d16` and their `_hi` forms, `ds_write_b8/b16` and `ds_write_b8/b16_d16_hi`. The access size is `Op::words`, the extension and half bits `Op::off1` (`kDsSign`, `kDsD16`, `kDsHi`, `kDsKeep`), all fixed at build time; `kDsKeep` (RDNA's `_d16` loads keep the register's other half, CDNA writes the whole register: the interpreter's `write_half_load`) is set from the target. The handler checks every lane's address first, branch-free (`addr + offset + size > lds_size` ORed), and hands the instruction back with nothing changed if one lane is past the LDS, which is the interpreter's job (the zero read, the write that goes nowhere, and the error for a work-group given no LDS, with its text); otherwise one counted loop (every lane on) or a walk of the exec mask, templated on size, sign and merge, with the lane's value made by the same arithmetic as `half_load` (the byte widened to 16 bits with its sign, then shifted for `_hi`). Stores run in lane order, so lanes that share a halfword end as they do one at a time, and a store takes the store gate like the other stores. A gather instruction (AVX2 `vpgatherdd`) was not used: it reads four bytes, past the end of the LDS for the last halfword, and on Zen 4 it is no faster than the scalar loads. The contiguous-run copy of the word forms was not added either: the profile's accesses are strided (a lane a row), and the remaining `h_dsn` share is 7.6% of the cycles.

## Round sp24 (bank passes): `histogram` and `shmembench` (branch `sp24-bank`, base `origin/main` 68d7d93b)

Phase 0 ranked CUDA sample `histogram` (35 ns per simulated instruction) and HeCBench `shmembench` (34 ns) near the top, with the shared-memory bank-pass counting the biggest item of both. Measured on server2 (Zen 5, Ryzen 9 9950X), one thread, SASS, `nvidia/rtx3060`, cpu 9, builds made from `git archive` (Release), no perf: the `tools/bench-amd/profile` SIGPROF sampler at 1 kHz.

### Where the cost was
* `histogram` (the 64-bin kernel `s_ThreadBase[data * 64]++` on random bytes, then the 256-bin kernel with shared `atomicAdd`): **80 M bank counts in the run, every one a full warp of 1-byte accesses** (counted with a temporary counter, not kept). Random bytes give no stride and no repeated shape, so the closed forms fail, the offsets table gives up (its back-off after a window with under a third of hits) and every access falls to the per-bank table of words in `sass_bank_passes_table`: 39% of the samples, plus `sass_bank_passes_widened` 4.7% (the 32-bit offsets widened to 64 bits first). The table is a search of the words already seen in the lane's bank, a loop whose length depends on the data, so on random addresses it mispredicts about once a lane: 130 ns a call on a micro-benchmark of 32 random lanes (`include/vgpu/exec/mem_counters.hpp` alone). The program's `++` is a load and a store of the same elements, so every second call asked for exactly the passes of the call before.
* `shmembench` (float4 `shm_buffer[tid + k * blockDim.x]`, a 16-byte element a lane in order): the counting is 28% (`sass_bank_passes_offsets` 17%, `count_shared_offsets` 4%, `thread_bank_memo` 4% and its `__tls_get_addr` 3%) and the move of the bytes, one 16-byte copy and four scattered register stores a lane, is most of the `h_shared<false/true>` 60%. The counting here is the memo working (a hit costs building the 32-offset key and comparing it): all of it for a shape that has a closed form (32 lanes end to end on whole words: `bytes / 4` passes).
* The thread-scaling and warp-sync items are other workstreams; not touched.

### What changed
1. **Bitmap counting** (`detail::bank_passes_bitmap`, taken first by `sass_bank_passes_table` for 1 to 4 byte accesses of up to 32 lanes): each active lane's word (and the next one when its bytes run over) goes into a bitmap of 32-bit rows, a bank's count goes up when its bit was not set, the answer is the biggest count. No branch depends on the data. It covers the 2048 words from the lowest word (8 KB of shared memory); a wider spread, or an address in the top 256 bytes of the space, takes the old table and the reference as before. 130 to 51 ns a call for 32 random lanes, 132 to 64 for a heavy-conflict shape (micro-benchmark, 1 thread).
2. **The warp asked last** (`BankMemo::last_offs`, `sass_bank_passes_offsets_kept`): while the offsets table is in its back-off, the last warp is kept whole (offsets, mask, width, passes) and the same warp again is answered by one comparison of 128 bytes. Only in the back-off, in a function of its own: the first version (checked on every call) put 3 to 5% on needle, whose memo hits pay for any extra work.
3. **A whole warp of 8 or 16 byte elements in order** (`tier_shared_wide`, called from `h_shared` for LDS/STS.64 and .128): lane `l` at `o0 + bytes * l`, `o0` a multiple of 4: one run, moved four lanes at a time with a 4x4 transpose (SSE2) between the run and the register rows, counted with the closed form (`bytes / 4` passes, as `bank_passes_progression` gives for these 32 lanes). Offsets are compared whole (a cluster rank in the high bits must be the same in every lane) and a run that would wrap 32 bits or the 24 bits an offset addresses is left to the general code. A function of its own (the 4-byte paths of `h_shared` keep their registers).

## Round sp24 (bh-cuda): a hang that was a missed poll (branch `sp24-hang`, base `origin/main` 68d7d93b)

Phase 0 ranked HeCBench `bh-cuda` (Barnes-Hut, `5000 2`) first by host ns per instruction (6,684) and last by thread scaling: 168 s at `VGPU_THREADS=1` and no end in 240 s at 2, 4 or 8 threads with every thread busy. The profile (step_warp 33%, `release_warpsync` 20%, `tier_ctl` 14%) looked like warp-sync bookkeeping. It was not. It was a launch spinning in one kernel until the step limit ended it.

### Root cause
* Counters per kernel (`VGPU_COUNTERS=1`, `VGPU_TIER_STATS=1`, 5000 bodies, one step, one thread, 100 s): 12.4 M warp instructions counted, but 976 M calls of `Runner::step_warp`, of which 390 M released a WARPSYNC and 390 M gave way at a YIELD. The tier's own native counts agree (BRA, ISETP, IMAD, LDG, BAR, YIELD, CALL, WARPSYNC about 390 M each); the launch counters do not show them because the kernel that spun was the one that then failed (see below). The three symbols are one spin loop, not three costs.
* A trace of one warp (`VGPU_SASS_TRACE=5 VGPU_SASS_TRACE_BLOCK=14 VGPU_SASS_TRACE_KERNEL=SortKernel`) shows the loop: `LDG.E.STRONG.SYS` of `startd[k]`, `YIELD`, `ISETP R7 >= 0`, `@!P0 BRA`, then `WARPSYNC`, `BAR.SYNC`, `BRA` back. Every block-14 sample in 976 M steps was in `SortKernel`.
* `SortKernel` (`while (k >= bottom) { start = volatile startd[k]; if (start >= 0) { ...stores...; k -= dec; } __syncthreads(); }`) waits for the thread that handles its cell's parent, which is in a higher block (the source says the grids "must all be resident at the same time"). The lockstep launch (`exec/lockstep.hpp`) runs such blocks together, but the kernel was not taken for a poller: `kernel_polls_loop` turns a loop down when it contains a store, a call, or an address that changes, and this loop has all three on the turns that find work. Run one block after another (one thread) or two at a time (2 to 8 threads), block 14 spun for ever on cells blocks 15 to 23 had not written.
* At one thread it "finished" only because the warp hit the instruction limit (`a warp ran N instructions`), the launch returned `VirtualGPU error [exec-limit]: SASS kernel _Z10SortKernel...: a warp ran N instructions (an infinite loop?)` (printed unless `VGPU_QUIET=1`; `VGPU_MAX_STEPS=3000000` shows it in seconds), and the program (which does not check) went on to the next kernel with a half-built sort order: its ForceCalculationKernel then did 12.2 M instead of 25.6 M warp instructions. The multi-thread runs were the same spin with 2 to 8 times the CPU. So the answer to "why does release_warpsync cost 20%": it does not, it is the YIELD/WARPSYNC/BAR turns of the spin.
* Control: `VGPU_LOCKSTEP=all` on the unfixed tree runs the same program, 5000 bodies, 1 step, in 0.70 s at 1 thread, 0.40 s at 2, 0.26 s at 4 (the original needed 100 s). `kernel_polls` was the only thing in the way.

### Change
`kernel_polls_conditional` (`src/sass/exec.cpp`), tried when `kernel_polls_loop` says no for a backward-branch loop: a loop with a strong, non-CTA global load whose value steers the work is a poll if some path through the loop body, the one the polled value does not send to the work, passes `kernel_polls_loop`. It follows forward branches depth first (the side of a branch on the polled value that skips the work first), leaves out what a guard on the polled value skips, allows a call to straight code without a store that ends in EXIT or RET (ptxas's `@!P0 CALL.REL.NOINC` to an `EXIT`, which bh's sort loop has), and is budgeted (20,000 steps, 400 instructions). It errs towards "no", as the test it extends. The PTX and AMD searches are untouched.

## Round sp25 (launch cost): the 35 us per launch is simulation, and radixsort2's loss is a one-thread rule (branch `sp25-launch`, base `origin/main` d6a98b42)

The question (from Phase 0): PolyBench `JACOBI1D` (20,000 launches of 16 blocks) does not speed up with threads (0.99x at 8), taking "35 us per launch regardless of threads", and HeCBench `radixsort2-cuda` scales 1.15x at 8 threads with wall 1.85 -> 1.61 s while user CPU rises 1.85 -> 2.22 s. Measured on server3 (Ryzen 7 PRO 8840U, Zen 4, 8 cores / 16 threads, shared with another session; 8 threads pinned to the 8 physical cores 0,2,...,14, or to cpus 0-15 where noted). A = origin/main d6a98b42, A2 = a copy of A's libraries made at the same time (the A/A control), W1 = the lockstep commit, W = both commits. 15 interleaved runs, medians.

### Where the time goes
* **JACOBI1D has no fixed cost per launch.** At one thread (`perf record`, 5 kHz, self time by symbol) `step_warp` is 27.4 %, the tier handlers, tier issue and SIMD kernels 36 %, memory loads, stores and counting 15 %, `init_block` 6.4 % (per block, 16 a launch); everything that is launch path (`Device::launch`, `Runner::run`, `build_tid_tab`, allocation, code fetch, `tier_program`, `code_at`) adds up to at most 2.2 % (about 1 us a launch), and the program's own code is 2 %. The counters say why a launch costs what it does: 10,000 launches of kernel 1 (2,944 warp instructions each) and 10,000 of kernel 2 (2,048), 49.9 M in all, in 0.96 s: 19 ns per instruction, the same as radixsort2's 17.7 ns. The "35 us" is 2.5 K instructions at 14-19 ns. It does not scale because the pool cap (`LaunchWidth`, 100 us of work per thread, round 12) keeps a 48 us launch on one thread, and nothing but the cap is in the way: with `VGPU_POOL_MIN_WORK_US=12` the same binary runs 0.46 s at 4 threads and 0.50 s at 8 (2.1x), and with 5 or less the 8-thread case thrashes (155 K voluntary context switches, 1.07 s). A hot pool hands a launch over in about 10 us (23 us a launch at 4 threads against 48 solo and an ideal 12).
* **radixsort2-cuda: 69 % of its instructions run on one thread at any `VGPU_THREADS`.** `VGPU_LOCKSTEP_LOG=1`: all 400 launches of CUB's `DeviceRadixSortOnesweepKernel` (9 blocks each, 72.6 M of the 105 M warp instructions: 69.1 %) are lockstep launches with "1 host thread(s)". The kernel polls its look-back flags, so it takes the lockstep path, and a lockstep grid of fewer than 16 blocks runs on one thread (`kLockstepOneThread`, #389: the answer of the RXMesh patch locks depends on the order blocks start in). The other 200 launches (histogram, 336 blocks) scale. Amdahl with 0.31 of the work parallel on 8 threads gives at most 1.37x, and the measurement is 1.14x. `VGPU_LOCKSTEP=0` (every launch on all threads, counters not comparable) gives 2.08 / 1.31 / 0.86 / 0.68 s at 1 / 2 / 4 / 8 threads, which is the scaling the program has.
* **The rising user CPU is the clock, not extra work.** `perf stat` at 8 threads: task-clock 2.85 s on 42.59 G instructions against 2.15 s on 42.45 G at one thread (instructions equal), cycles 10.75 G against 10.34 G, **3.78 GHz against 4.82 GHz**: the laptop part runs 22 % slower per core with eight busy, so the same work costs 30 % more CPU time. The pool's spinning is not it (`worker_main` and `run_parallel_raw` are 0.2 % of the samples). (A 16-thread-wide box with a fixed clock would not show this rise.)

### Changes
1. **Small lockstep grids whose waits are only loads use the host threads** (`src/sass/exec.cpp`, `include/vgpu/exec/lockstep.hpp`; SASS engine only). The poll search now says what a loop polls with: a strong load, or an atomic that returns its old value (a lock being taken; `kPollLoad`, `kPollAtomic`, cached per kernel). A kernel with atomic polls keeps the fixed-order rule (the patch locks). A kernel that polls with loads only (the look-back, flag chains, `producer_consumer`) spreads a grid of two blocks or more over up to `blocks / 2` threads, each holding its share of the blocks from the start (a block may wait for the last one). `VGPU_LOCKSTEP=all` is unchanged. Not done: the PTX engine (`ptx_kernel_polls`) and the AMD engine have their own searches and the same one-thread rule.
2. **A small launch goes wide on trial and stays wide only while the pool beats one thread** (`src/exec/worker_pool.cpp`, `PoolTrial`). A kernel the 100 us rule holds to few threads gets the width a 12 us floor allows, for eight launches; the first is not judged (it wakes cold workers), and the best of the other seven decides: wall time under 70 % of what one thread would take keeps the width (judged again every eight launches), otherwise the kernel is held to the old width for 256 launches, doubling after each loss to 65,536. `VGPU_POOL_MIN_WORK_US` set by hand is the old fixed rule. `VGPU_POOL_TRIAL_LOG=1` prints each verdict. The estimate of one thread's time is the kernel's per-block cost from the busy time of its last launches, which is the same the cap uses.

## Round sp24 (fingerprint): the first lockstep look of a launch waits for what the last look cost (branch `sp24-fingerprint`, base `sp19-ptx` bccfa63b)

The question: the lockstep fingerprint (the fold of every warp's registers and the shared memory of each resident block, `lockstep_worker` in `include/vgpu/exec/lockstep.hpp`) was still 25.6% of radixsort2's cycles after the eight-chain fold. Is it the fold, building the input, or the call, and what is the cheapest change that moves no result?

### Diagnosis (server3, Zen 4, cpu 13, `VGPU_SASS=0`, `nvidia/rtx3060`, one thread, RelWithDebInfo with `-fno-omit-frame-pointer`)
* `perf record -F 3000 --call-graph dwarf` puts 33.0% of radixsort2's cycles in the `{lambda(unsigned int)#1}` of `launch_grid` (the host thread's body, with `run_lockstep` and `lockstep_worker` inlined into it); `perf annotate -l` on that symbol puts **88.7% of its samples on two source lines, `lockstep.hpp:131` and `:132`, the fold's chain step** (`s[i] = (s[i] ^ w[i]) * kPrime; s[i] ^= s[i] >> 29`), 1.3% on the loop line (`:130`) and 2.6% on the `memcpy` of the words. So it is the fold itself, not the input and not the call.
* Why a rule that bounds a look to a thirteenth of the time (`check_every = max(250 us, 12 x the look's cost)`) still gave a third: counters in `lockstep_worker` (temporary, not shipped) on radixsort2 `-float -keysonly -n=65536`: **400 launches, 400 looks, exactly one look per launch, 0 of them finding the blocks standing still, 0 naps**; 3.5 s of the 9.7 s the workers ran was those 400 looks (about 8.7 ms for 9 resident blocks, a PTX register file being every virtual register of the kernel). A launch of the sort lasts about 24 ms, its blocks store nothing for the first 250 us, so the one look every launch makes is the first one, at 250 us, before the 12x rule has measured anything. sortKV: 32 launches, 32 looks, 0.45 s of 0.97 s. SYRK and the other non-lockstep programs: 0 launches in `lockstep_worker`.
* A look decides one thing, whether the thread sleeps between passes (`same >= 2`). It reaches no register, memory, counter or error text; when it is made is already a function of the wall clock (250 us, then 12x its own cost).

### What changed
`lockstep_worker` keeps, per call site (so per engine: PTX, SASS, AMD), what the last look cost **for each resident block** (`look_ns_per_block`, a relaxed atomic, 0 until a look has been made). A launch that has not looked yet takes its first look after `max(250 us, 12 x that x the blocks resident now)`, at most 500 ms (`lockstep_first_look`); once it has looked, `check_every` is what it was (`max(250 us, 12 x the look just made)`). Both helpers are `[[gnu::noinline]]`: see the layout paragraph below. Nothing is skipped or approximated: when a look is made it folds exactly what it folded.
Same bits by construction: the only input changed is the time of a look, which already was a wall-clock quantity, and the look's only effect is the nap. A block that stands still is still found out (a look 250 us in when nothing has been learned, the third equal look sleeping, as before). The cost of the change is that a launch with big register files and a block really waiting for another is found waiting later (by up to 12 looks' worth, at most 0.5 s for the first look), which spins a host thread, with `yield()` between passes, a little longer before it naps.
Not done, and why: folding only the live registers (the kernel's virtual register count is known, liveness is not; a dead register that differs would make two looks differ, a different fingerprint rule) and dirty-tracking (a spin loop writes registers every turn, so a dirty block would be folded every time; the blocks that are not dirty are not the cost here).

## Round sp26 (amd-gather): float division rows, `v_ldexp_f32`, and a packed handler built for AVX2 (branch `sp26-amdgather`, base `origin/main` dfbf2dc1)

The question (Phase 0 ranking): `amd-polybench/SYR2K` costs 51 ns a wave instruction (`MemoryManager::load_batch` 37 %, `wave_scalars` 17 %, `h_pk` 9 %, `tier_global` 8 %) and `amd-hecbench/bilateral` 50 ns (`h_div` 32 % plus libm `modff` / `ldexpf`). Measured on server2 (Zen 5, `nice -n 19`, `VGPU_THREADS=1`, cpu 13, the other cores shared with CI and other sessions: load 4 to 10), the programs hipified and built for gfx942 (`hipcc -O2 -ffp-contract=off`), profiled with the SIGPROF sampler of `tools/bench-amd/profile` on a `-g` build.

### Is the AMD gather the NVIDIA one? Yes: nothing to change in `load_batch`
`--lines` on SYR2K puts 26 % of all samples on one line, the `relaxed_load` of the word in `gather_loads` (`src/core/memory.cpp`), and 3 to 4 % on each line beside it (the offset, the chunk pointer, the return): the loop waits for its loads, as the NVIDIA experiment found. The reason is in the kernel's addresses. `b[j * NJ + k]` and `a[j * NJ + k]` put the lanes of a wave 4096 bytes apart (NJ = 1024 floats), and the next `k` reads the next four bytes of the same 64 lines. Every address of the wave maps to the same L1 set (64 sets of 64 bytes), 64 lines compete for 12 ways, so each `k` misses L1 for every lane and the 16 `k` that would share a line never hit. A stand-alone probe on the same CPU (64 lanes, 1024 k, 4-byte loads, a 64 MiB array) reads **1.28 ns a load at strides 4096, 8192 and 16384 against 0.21 ns at 4160, 8256 and 16448**: six times, from set conflicts alone. The host layout is the guest's own (a 64 KiB chunk holds 16 of the lanes' lines at the guest's stride), so no change to the loop reaches it: a prefetch pass fetches lines the next `k` evicts, and the NVIDIA experiment measured split passes at 13 % slower. Skewing chunk bases does not help either (16 lanes of one chunk already exceed the 12 ways). Not changed; a padded host layout would be a memory-manager redesign, not a gather change.

### What bilateral's time was

### What changed
1. **`v_div_scale_f32`, `v_div_fmas_f32`, `v_div_fixup_f32` on whole rows** (`h_div_rows_body`, `amd/src/gcn_tier.cpp`; `div_scale_row_plain_f32`, `div_fixup_row_plain_f32` in `amd/src/gcn_divide.hpp`). The lane functions already reduce the usual case to tests of the exponent fields; the row forms apply those tests to the whole wave without a branch (a loop the compiler vectorizes), and when every lane is in the plain case the result is a row operation: scale leaves S0 and clears the condition bits, fixup is `|S0|` with `sign(S1) xor sign(S2)`, fmas with no condition bit in an active lane is the fused multiply-add of the row (a NaN in an active lane still hands the instruction back to the interpreter, as before). A row with one lane outside the plain case, and the double forms, take `h_div` (the old lane code, untouched, now `noinline`). Built twice like the other float handlers (baseline and AVX2, picked at decode).
2. **`v_ldexp_f32`** (`h_ldexp_body`, `divide::ldexp_f32_exact` / `ldexp_f32_shift`): a row whose lanes are all normal numbers that stay normal gets its exponent field moved (`bits + (k << 23)`, exact); any other row, and any with an output modifier, goes to `h_f32` and libm as before. ## Round sp26 (zero-copy): host-pinned memory as runs and host batches (branch `sp26-zerocopy`, base `origin/main` dfbf2dc1)

The worst non-tensor rows of Phase 0 were the HeCBench `zerocopy` program on both engines (`amd-hecbench/zerocopy` 183 ns an instruction, `hecbench/zerocopy-cuda` 98): a vector add over three `cudaHostAlloc(mapped)` / `hipHostRegister` buffers. Profile first (server3, Zen 4, `perf record -e cycles:u`, one thread, whole program; the program's own `random()` initialisation is 15 to 37 % of every profile and is left out below):

* AMD: `tier_global` 15.8 %, `lookup_host` 11.8 %, `load_scalar` 10.7 %, `scalar_location` 10.1 %, `load_words` 8.6 %, `store_words` 4.2 %, `store_scalar` 4.2 %, `__tls_get_addr` 3.5 %. `memory_run` asks `load_run`, which declines every address that may be in a host mapping, and `wave_scalars` asks `load_batch` / `store_batch`, which decline it too, so each of the 64 lanes went through `load_words` -> `load_scalar` -> `scalar_location` -> `lookup_host` (a thread-local cache: the `__tls_get_addr`).
* SASS: `exec_mem` 25 % (the 32-lane loops), `find_ordinary_miss` 4.7 % + `lock_shared` 1.6 % + `batch_addresses_ok` 2.9 % + `batch_ok` / `load_batch` / `store_batch` / `run_allocation` ~3 %, `host_batch_hit` 3.3 %. The tier's `h_global` asked `load_run` (declines), then `load_batch` (a lookup in the allocation table under the shared lock for an address that is in no allocation: a miss, every warp), then `exec_mem`, which makes the addresses a second time and ends in the host batch.

Changes (all of them the same accesses as before, in the same order, each element the relaxed atomic access of its width that `load_scalar` / `store_scalar` make on host memory):

* `MemoryManager::load_host_run` / `store_host_run`: a run wholly inside ONE host mapping, one `lookup_host` for the run. Declines (and the lane path meets the error) for a fault armed, a misaligned run or host bytes, a run that leaves the mapping, a store to a read-only mapping.
* AMD `memory_run` (words, pairs, sixteen-byte quads as two 8-byte elements, as `load_quad` does on host memory) tries the host run after `load_run` / `store_run`; `wave_scalars` asks `host_load_batch` / `host_store_batch` first when the first address may be in a host mapping.
* SASS: `tier_ops.inc` `h_global` and `exec_mem` try the host run after the ordinary run and the host batch before the ordinary batch (a store resets `idle_yields` as the host batch always did; a load of one address stays on the single-read path of `exec_mem`).

## Round sp30 (atomic-heavy real programs): MATCH.ANY classes by hash

Base: origin/main 2db5dd65. Server2 (Zen 5), nice 19, one builder, `VGPU_GPU=nvidia/rtx3060` (SASS), one thread, Release/LTO.

### Why atomicCost is big and slow
atomicCost (HeCBench) allocates `length = 922,521,600` elements: two device buffers and two host `malloc` buffers of `length / N` values each, so about 4 x 7.4 GB for the FP64 case. Phase 0 saw 14 GB RSS because the memory manager spills device chunks to its file once the host runs short. This is the program's own memory: with the constant in the binary divided by 16 (the three `mov $0x36fc9000,%edi` immediates, 57,657,600 threads, same kernels), RSS is 1,810 MB = 4 x 461 MB, i.e. exactly the four buffers, and the simulator adds nothing per address (zero-filled chunks of `cudaMemset` are not materialised; `atomicAdd` touches only the pages the kernel writes). The AMD build is stopped by the host-memory guard on a box with 1.8 GB free, which is the guard working. Nothing to cut in memory.
Speed: the reduced run is 276 M warp instructions in 4.1 s at one thread (about 15 ns per instruction), the profile is flat (`step_warp` 20 %, `exec_mem` 7 %, `init_block` 8 % of which most is the per-warp register-file clear, the atomic lane loops `global_lanes` about 4 %). ### The hot spot that was there: atomicAggregate
atomicAggregate (warp-aggregated increments built on `__match_any_sync`) spent 28 % of its samples in the tier handler `h_match`. ## Round sp28 (lockstep on the PTX and AMD engines): small grids of load polls use the host threads there too; the AMD pool is left as it is (branch `sp28-lockstep`, base `origin/main` fe3c0a02)

The question: #501 (round sp25) stopped the SASS engine from holding a lockstep grid of fewer than 16 blocks to one host thread when its kernel only polls with loads (CUB's onesweep look-back: radixsort2-cuda 2x at 8 threads), and let a small launch go wide on trial (`PoolTrial`, JACOBI1D 2x). The PTX engine (`VGPU_SASS=0`, `ptx_kernel_polls`) and the AMD engine (`amd_kernel_polls`, its own pool `amd/src/gcn_pool.hpp`) have their own poll searches. Do they have the same two blind spots? Measured on server3 (Ryzen 7 PRO 8840U, Zen 4, 8 cores / 16 threads, shared with another session, load 1 to 7 during the timed runs), 15 interleaved runs, medians; A = `origin/main` fe3c0a02, A2 = a copy of A's libraries made at the same time (the A/A control), W = this branch's lockstep commit.

### Blind spot 1, the one-thread rule for a small lockstep grid: both engines have it
* **PTX.** `VGPU_LOCKSTEP_LOG=1` on radixsort2-cuda (`-float -keysonly -n=65536`, `VGPU_SASS=0`): all 400 launches of CUB's `DeviceRadixSortOnesweepKernel` are lockstep launches of 9 blocks on "1 host thread(s)" at `VGPU_THREADS=8`, so the engine's biggest kernel runs on one thread whatever the setting (the same 69 % of the instructions as on SASS). The lockstep shape call was `lockstep_shape(blocks, resident, threads)` with no `small_grid_spreads`.
* **AMD.** Same call (`lockstep_shape(groups, capacity, nthreads, /*ranges=*/true)`); the checked-in hipcc programs show it: `lockstep.gfx942 queue` (a 10-group producer/consumer) reports 1 host thread at `VGPU_THREADS=4`. No real AMD look-back program is available on server3 (hipcc is only on server2, which belongs to another session), so the AMD timing below is a synthetic look-back kernel, not a real program.

### The change
Both poll searches now return what a kernel polls with (`kPollLoad`: a strong load; `kPollAtomic`: an atomic that returns its old value), over every loop of the kernel (a kernel with a lock loop anywhere keeps the fixed order, whatever its other loops wait on: the first loop found no longer ends the search), cached on the function/kernel in the field that held 0/1 (`PollsFlag`: now 0, 1, 2 or 3). A launch whose waits are loads only passes `small_grid_spreads` to `lockstep_shape`, as SASS does: up to blocks / 2 threads, every block resident from the start. A kernel with any atomic poll (the RXMesh patch locks) and `VGPU_LOCKSTEP=all` keep the one-thread, fixed-order rule. The constants and the rule are shared: `kPollLoad`, `kPollAtomic` and `lockstep_loads_only(mode, kinds)` in `include/vgpu/exec/lockstep.hpp`, used by SASS, PTX and AMD. Counters at more than one thread: the one user-accepted exception of #501 (poll-count jitter on look-back kernels at >1 thread) now applies to the PTX and AMD engines too; nothing wider.

## Round sp31 (the table's reader lock on per-lane 16-byte accesses; branch `sp31-readerlock`, base `origin/main` 2db5dd65)

Round sp29 found `BigReaderLock::unlock_shared` 18% and `lock_shared` 6.7% of cycles in HeCBench `bh-cuda` (SASS, one thread). Where it comes from: `BigReaderLock::lock_shared` is one `lock xadd` on the thread's own slot plus a read of the writer flag, `unlock_shared` a second `lock xadd` (uncontended, one thread's own cache line: the cost is the two serialising atomics, about 40 cycles a pair, and the sampler books the second one's wait on `unlock_shared`). The lock is taken once per call of `MemoryManager::resolve`, and that is called once per lane by `MemoryManager::read` / `write`, which is what `tier_global16` (LDG.128 / STG.128) and every unaligned access use for each active lane that is not one run of 16-byte pieces. Scalar accesses (`load_scalar`, `resolve_scalar`) and the batches already ask the thread's memory of recent lookups first (`find_ordinary`, validated by the lock's epoch) and take the lock only on a miss. `read` and `write` did not.

### What changed
`read` and `write` ask `find_ordinary` first through `resolve_bulk`, then `resolve` on a miss (and whenever `card_resident_ > 0`, where `resolve` asks the card gate before it looks). Same answer by construction: a hit is an allocation of `live_` that holds the whole access, which is what `resolve` returns for an access with no page slack; an access that is not a hit (off the end, freed, mapped, unknown) is `resolve`'s, errors and all. The hit is under the same epoch rule the scalar path has relied on since the lookup memory was introduced (a free calls `note_free` before the allocation is taken apart; an allocation changes no remembered answer). Nothing about when the lock is held across the copy changes: `resolve` released it before `read_chunks` did its copy both before and after.

Not changed: batches, `find_ordinary_miss`, `batch_ok`, `run_allocation` and the host-mapped run of PR #507 (branch `sp26-zerocopy`, not needed: no file overlap beyond `memory.cpp`'s unrelated hunks). Not done: a per-warp 16-byte batch. Branch `sp26-tensor` (PR #510, open) already does the loads ("128-bit global loads as two batches of 8-byte pieces"), and with it bh-cuda has no lock share left (0.946 s at one thread against 1.28 s on main, `perf`: `load_batch` 9%, no `resolve`). ## Round sp27 (AMD gather): a wave's load reads each repeated address once (branch `sp27-gather`, base `origin/main` dfbf2dc1)

### Where the cost was
Phase 0 put `MemoryManager::load_batch` at 37% of amd-polybench/SYR2K. SYR2K's kernel (`c[i][j] += a[i*NJ+k] * b[j*NJ+k] + b[i*NJ+k] * a[j*NJ+k]`, work-groups of 32 x 8) makes a wave of 64 lanes = two rows `i` of 32 columns `j`. Of its four loads a `k`, two (`a[i*NJ+k]`, `b[i*NJ+k]`) have **one address in each half of the wave** (32 lanes at one address), and two (`b[j*NJ+k]`, `a[j*NJ+k]`) are gathers whose **second half repeats the first half's 32 addresses**. `wave_scalars` handed all 64 lanes of every one of them to `load_batch` (14 instructions a lane). So 256 lane loads a `k` did the work of 68.

### What changed
`Machine::load_wave_repeats` (`amd/src/gcn_exec.cpp`, out of line, called by the whole-wave branch of `wave_scalars` for loads after the "every lane at one address" test): (1) each half of a wave of 64 at one address: two reads, 32 lanes filled from each; (2) a wave of 64 whose lanes 32..63 have lanes 0..31's addresses, on one host thread only (`!conc()`): the first 32 are read and copied; (3) groups of four or more neighbouring lanes at one address (lanes 0..3 and the last four lanes are tested): the distinct addresses are read and expanded. (1) and (3) are the rule `wave_scalars` already had (a lane that follows a lane with the same address takes that lane's value), applied before the read rather than after it, so they hold with threads too; (2) needs that no other thread writes between the two reads. The memory manager sees a subset of the same addresses with the same first lane, so it accepts and declines exactly as for the whole wave (a decline returns false and the lanes go one at a time, as before). Nothing else changed: counters are counted in `tier_global` before this.

### Changes (results, counters and error text unchanged; every accumulation order unchanged)
1. **HMMA from the registers** (`mma_avx512_frag_m16n8`, `include/vgpu/exec/tc_ampere.hpp`; called by `hmma_k` in `src/simd/kernels.inc` for f16 and bf16 operands with an f32 accumulator, K 8 or 16, at the AVX-512 level). The fragments were widened to floats, copied into A 16 x K and B K x 8, put through `mma_avx512_chunked_f`, which decoded them once more and paired the rows, and the answer was shuffled back. Now the 32 contiguous bytes of two rows are converted once and permuted into the 64-bit (row 2p, row 2p+1) element the units broadcast; B is transposed and doubled as 16-bit halves; the accumulators and the answer cross between the registers and the unit order by one `vpermt2d` / `vpermd` each. The units, the declines (`return false` before anything is written; `hmma_k` then runs as before) and the lanes finished by `mma_f_fix512` are the old kernel's; the cold path rebuilds the row-major floats from the registers. For f16 the `0xffffe000` mask and the float-subnormal flag are not computed (a half's float has the bits clear, a field of 0 is a zero, and 255 is declined by the maximum).
2. **IMMA from the registers** (`imma_frag_m16n8`, new `include/vgpu/exec/imma_frag.hpp`; `h_imma` takes it for s8/u8 operands, 16 x 8 x 16 and 16 x 8 x 32, no `.SAT`, at the AVX-512 level): the 16-byte runs of the registers are widened to 16-bit pairs and summed by `vpmaddwd`; a 32-bit wrapping sum is the same in every order, so the answer is the tile kernel's. The result is written with `tier_store` (a row copy or a blend) instead of a store a lane, which was half of `h_imma`'s own time.
3. **LDSM** (`include/vgpu/exec/ldsm.hpp`): the 32 row addresses are checked by `shared_window_inside_warp` (the same answer as `SharedWindowCheck` over the 32 addresses), and the words move as 16-byte copies (plain) or an 8 x 8 transpose of halves (`.MT88`; column c of the result is the 16 bytes `out[4c..4c+3]`).
4. **128-bit global loads off a run** (`tier_global16`, `src/sass/tier_ops.inc`): a warp whose lanes were not on consecutive 16-byte pieces made a `MemoryManager::read` (a lock and an unlock) for each lane; the lanes now go as two `load_batch` calls of 8-byte pieces, as LDGSTS already reads them and as the run path of the same function does. A batch the memory manager declines has done nothing and the old lane loop runs.

## Round sp27 (amd-f64): double division rows, `v_ldexp_f32` in integers (branch `sp27-amdf64`, base `sp26-amdgather` 0e6d09c4)

### What changed
1. **`v_div_scale_f64`, `v_div_fmas_f64`, `v_div_fixup_f64` on whole rows** (`h_div64_rows_body`, `div_scale_row_plain_f64`, `div_fixup_row_plain_f64`): the f32 rows of sp26 for doubles. The verdict looks at the ACTIVE lanes only (a lane the instruction does not write holds a stale register, zero in a diverged wave, which would make nearly every diverged row "special"). The first pass reads only the high words (32-bit lanes, which the vector units do whole); the two cases the mantissas decide (the reciprocal's exponent just below the largest, the quotient's at the denormal edge) are only counted there and looked at in full, through all 52 bits, in a second loop. 2. **`v_ldexp_f32` for every lane in integers** (`divide::ldexp_f32_bits`): libm's `ldexpf` bit for bit (zero and infinity as they are, a NaN quieted as `x + x` does, an overflow the signed infinity, a result below the normal range rounded once to nearest even, a denormal operand normalized first). sp26 sent a row to libm when ONE lane was not a normal number that stays normal; in `bilateral` that is nearly every row (exponentials that underflow), and `ldexpf` with the `modff` under it was 21 % of its samples. A row with such a lane now goes through `ldexp_mixed` (integers, no libm); the all-exact fast path is unchanged. A NaN among the active results still goes to `h_f32` (a no-op today: `v_ldexp_f32` has the pass rule, 0 hand-backs).
The new definitions (`h_div64_rows_*`, `ldexp_mixed`) are at the END of `gcn_tier.cpp`, declared where the old code was.

## Round sp32 (memoisation): measured, not built (branch `sp32-memo`, base `origin/main` 7d8d98a4)

Question: can an opt-in, launch-level result cache (`VGPU_MEMO=1`: key = kernel, grid, block, shared bytes, argument bytes, content of every device range the launch can read; a hit replays the written bytes and the counters) skip enough work, soundly, to matter? `docs/perf-design/03-result-memoisation.md` measured fixed points on the argument-reachable allocations only. This round measured the real key, over every live allocation, on the pantheon workloads and on the Phase 0 corpus. Nothing was built: the gate below failed on two of its three conditions. The instrument was throw-away (a per-launch hook in `Device::launch`, kept as a patch outside the tree), and nothing in this tree changes behaviour.

### What was measured
Release build of origin/main plus the hook, server2 (Zen 5), one thread, `taskset`, one heavy job at a time. For each launch the hook reads every live allocation (so the key covers the whole read set, a superset of what any kernel can read through device pointers), hashes it by 4 KiB page, and computes: the key; the hash of all memory after the launch and a digest of every counter (to check that equal keys give equal results); the launch's warp instructions and wall time; the pages that changed during the launch (what a hit replays) and the pages that changed between one launch's end and the next one's start (host writes). Corpus: the first 41 of the 124 NVIDIA programs of Phase 0 (all of PolyBench/GPU and Rodinia, then HeCBench in order; the run was stopped there because each launch reads all live memory and the box is shared).

### What a build would need (so the next round does not repeat the measurement)
* The read-set key is not the problem; the cost of getting it is. A different formulation avoids hashing memory at all: identify the memory state by its history, `S(n+1) = H(S(n), launch descriptor)` for a cacheable launch and `H(S(n), hash of the bytes)` for each host write, fill and copy (all cold, all in `MemoryManager` and the runtime copy paths), starting from the empty device. Equal history means equal state when execution is deterministic, which is what the 0 mismatches above test. A launch the cache cannot represent (atomics across blocks, printf, device malloc, cooperative or cluster launches, textures, host-mapped or managed memory, another device writing, any fault armed) sets the state to a fresh unique id, and nothing hits until the next whole-memory canonicalisation. Cost of a hit: one lookup and the replay; cost of a miss: nothing on the key.
* What remains is capturing the write set of a miss. Without store tracking it is a before/after diff of live memory, the brute-force figure again, so it needs a budget (record only while recording costs under 5 % of the simulated time so far; an unrecorded launch poisons the state). That is the shape that could meet condition 2 by construction, at the price of a lower hit rate on the corpus's first run.
* Soundness items found while reading the launch path: the key must also cover the kernel's code and its constant banks (the study keyed on the kernel name), `__constant__` and module globals (module globals are live allocations, so covered by the content hash, but not by a history key unless module load is a hashed event), textures and surfaces, the launch environment (`VGPU_THREADS`, lockstep mode, step limit), and the profile. Replay must call `report_counters` with the stored `LaunchStats` (so `VGPU_COUNTERS_FILE` records match, apart from the launch sequence number) and `telemetry_->note_kernel`.
* The pantheon logic that sits around the launch (verification passes, `--inject_error`, `vgpu fault`) must keep running the kernel: any armed fault, `VGPU_MAX_STEPS`, race detector, tracing, `--profile` and the debugger turn the cache off.

## Round sp35 (launch-level result caching): built, tested, measured (branch `sp35-memo`, base `origin/main` 9f80d40e)

`VGPU_MEMO=1` (opt-in, off by default and then bit for bit what it was) skips a launch whose result the device has already produced: it applies the stored write set, counters and kernel digest instead of running the kernel. Round sp32 measured that equal keys give equal results (0 mismatches in 473,537 hits) and that the one thing that blocked a build was the cost of the key and of capturing a write set. This round built the design that study recommended and measured it. Knobs: [cli.md](../../cli.md) (`VGPU_MEMO`, `VGPU_MEMO_DIR`, `VGPU_MEMO_MAX_MB`, `VGPU_MEMO_MEM_MB`, `VGPU_MEMO_ENTRY_MB`, `VGPU_MEMO_BUDGET`, `VGPU_MEMO_EVENT_CREDIT_MS`, `VGPU_MEMO_VERIFY`, `VGPU_MEMO_STATS`, `VGPU_MEMO_FINAL_HASH`). Code: `include/vgpu/memo.hpp`, `include/vgpu/runtime/memo.hpp`, `src/runtime/memo.cpp`, `src/core/memo_hash.cpp`, the hooks in `src/core/memory.cpp` and the launch in `src/runtime/runtime.cpp`.

### Design
* **State by history, not content.** A device's memory is named by `S`, a 128-bit hash chain. A host write, fill, device-to-device copy, allocation or free is an event: `S = H(S, event)`, and a write includes the hash of the bytes it writes (already O(bytes) to copy). A launch is an event too, and its description is its cache key: `key = H(S, kernel code identity, grid, block, shared bytes, argument bytes, launch environment)`. `S` starts from the empty device (the profile and the identity of the simulator's own object file, so a rebuild never replays an older build's results). Nothing reads device memory to form a key.
* **A launch that changes no byte leaves `S` as it was.** That is what makes a loop of idempotent kernels hit within one run: the second launch of `fixed7` finds memory unchanged (recorded, with an empty write set, and `S` stays), the third hits. A launch that changes memory moves `S` to its key, so a repeat of the whole history (a second run of a deterministic program) finds every key again from launch 1.
* **Poison.** A launch or call the cache cannot represent sets `S` to a fresh value no other run has (a process seed and a process-wide counter), so nothing before it can match anything after it. It is never an incorrect hit; at worst it is a lost one. Table below.
* **Key.** Kernel code identity is a 128-bit hash of the module's PTX text or cubin image plus the kernel name and engine (SASS or PTX), so constant banks, `__constant__` data in the image, and the code itself are covered; `__constant__` and `__device__` variables' contents are device memory and so are part of `S`. Also in: grid, block, dynamic shared bytes, work dimension, scheduler and seed, step limit, heap and stack limits, whether a graph launched it, the argument bytes, every `VGPU_*` variable that is not one of the 14 prefixes known not to change a result (output paths, statistics, the thread count), the launch environment strings the engines read (`VGPU_TC_EXACT`, `VGPU_FASTPATH`, `VGPU_STRICT`, `VGPU_LOCKSTEP`, ...), whether blocks run in order (`VGPU_THREADS=1`), the device profile (every limit) and the build's identity.
* **Write-set capture (the hard part).** A miss that is worth recording is run between two hashes of the 4 KiB pages of the allocations the launch could write. Those are: every allocation an argument word points into (any byte offset, so structs of pointers count), the module's global variables, and, as soon as a device pointer may be stored in memory (a pointer-like word, an address in the device window, was written by the host or by a recorded launch, or a launch ran unrecorded), every live allocation. Pinned and managed memory is not in that list (a diff does not see host memory): the memory manager notes any access that resolves into a mapping, and a launch that made one is not cached and poisons what follows, whatever its arguments were. A mapping no kernel touches (pinned staging buffers, the usual case) costs nothing. Pages of chunks that were never written, or are one repeated byte, are hashed without being read. The hash of a launch's after-state is kept as the next launch's before-state while nothing touched the allocation (host events invalidate the allocations they write), so a loop of launches costs one pass, not two. The pages that changed become runs (a run of one repeated byte is stored as one byte). A budget decides whether to record: recording is allowed while its cost so far plus this launch's estimate stays under `VGPU_MEMO_BUDGET` (3 %) of the kernel time of the launches that ran, plus 150 us of credit; a launch that is not recorded simply runs, and the history advances by it as for any launch (its effect is a function of the history, as for every launch, under the same determinism assumption the study measured). **The hashing of the bytes of host writes is part of the same budget (round sp38):** a host write whose hash does not fit (its own credit, `VGPU_MEMO_EVENT_CREDIT_MS` = 8 ms, then the same 3 % of kernel time) is not hashed and poisons the history instead, so it can never give a wrong hit; hashing past the credit eats the pool that recording draws on; a cache that went dormant keeps no history at all.
* **A hit** checks every run against the allocation table (a refused replay leaves memory untouched and runs the kernel), writes the runs in a scope that makes them no events, reports the stored `LaunchStats` through `report_counters` (so `VGPU_COUNTERS_FILE` records, minus the launch number and pid, and `vgpu ncu` are what a run gives), tells telemetry, and writes the kernel digest, so `VGPU_KERNEL_DIGEST` is reproduced exactly.
* **Store.** In memory (LRU, `VGPU_MEMO_MEM_MB`) and, with `VGPU_MEMO_DIR`, on disk: one file per key in a 256-way fan-out, written to a temporary name and renamed, a hash of the whole file at its end (a file that does not parse or does not hash is deleted and is a miss), least recently used removed past `VGPU_MEMO_MAX_MB` (a hit touches the file). Which keys exist is learned a bucket at a time, so a miss costs a hash lookup and not a failed `open`.
* **Verify mode** (`VGPU_MEMO_VERIFY`): a hit is run for real too, with the write set captured, and compared byte for byte with the stored one, counters included.
* **Off** (the default; also off under `VGPU_HOST_GPU`, AMD devices, and more than one device): `Device` holds no cache, the memory manager's sink pointer is null, and the one per-call cost is a null test in cold paths (`write`, `fill`, `copy_to`, `alloc`, `free` and the virtual-memory calls). Results are the ones of main.

### Measurements
Server2 (Zen 5, Release with LTO, GCC 13), one pinned core, `nvidia/rtx3060`, `VGPU_THREADS=1` for the corpus (the Phase 0 convention), the machine-wide lock taken by the harness itself so that a run's time is the program's and not the wait for its turn (the box also ran another session's long jobs, which is why the corpus tables below are not complete: see "What was not run"). `tools/bench/memo/memo_diff.py` (corpus and repo e2e programs: off, off again as the A/A control, cold, warm, and in correctness mode a verified run; medians of 3 alternating repetitions), `memo_pantheon.py` (the workloads), `tables.py` (the tables). Per-program tables are in `docs/perf-design/data/memo-sp35-*.md`.

**Per-process cost.** Switching the cache on costs a process 0.16 ms in memory and 0.32 ms with `VGPU_MEMO_DIR` on a 2.6 ms program (`samples/vectorAdd`, 40 alternations of off, off, memory, cold, warm: medians 2.63, 2.64, 2.79, 2.95 and, warm, 2.35 ms). **What was not run (and why).** The server was shared with another session's long jobs holding the machine lock for hours, so: the corpus overhead was measured on the 54 programs of 50 ms or more only (the 35 smaller ones were measured on an earlier build, before two fixes, and are not in the table); the 13 longest corpus programs were left out of the differential; the `VGPU_MEMO_BUDGET=inf` table (what recording every miss would cost) was not produced; the corpus differential and the pantheon runs are of build `94d2a99d`, while `82055089` and `6a5fc97a` then followed the review's findings and the estimate fix (unit tests, `memo_api_matrix` and the overhead table were redone on `6a5fc97a`).
Not covered by design: AMD devices, more than one device, programs that use virtual memory management or IPC.

### Caveats
* **Determinism.** A cached launch assumes the kernel gives one answer from the same inputs. A kernel that races without atomics on several host threads gets one of its answers frozen (atomics on several threads, `%smid` reads and `%gridid` reads are refused); `VGPU_THREADS=1` makes every launch ordered.
* **Reach.** A kernel that writes outside the allocations it can reach (an out-of-bounds write that lands in a neighbour) is not diffed; pointers stored in memory are found by a scan of 4-aligned words in the device window, so a pointer split across two separate host writes, or encoded, is not found while it is the first pointer stored (after the first launch that runs unrecorded the cache assumes pointers anywhere).
* **Host threads.** Host calls from another thread are detected only when they overlap a launch.
* **Indirect calls.** The scan for device-runtime calls follows static calls: a kernel that reaches `vprintf`, `malloc` or `cuda*` only through a function pointer is not recognised (a device malloc is still caught afterwards).
* **Keyed to the build.** The simulator's own ELF build id is in every key, so a rebuild starts a new cache (old entries age out under the size cap).
* **Telemetry.** A hit takes no time, so utilisation and the pantheon workloads' reported rates are meaningless with it on (they already measure no hardware).
* **Disk.** Entries are trusted as the program that wrote them; the checksum guards against corruption, not tampering. Entries other processes add are seen only when their bucket is first read.

## Round sp33 (JIT control flow): loops, branches, S2R and the uniform datapath inside generated code (branch `sp33-jit`, base `origin/main` 7d8d98a4)

Full write-up: [docs/perf-design/round15-jit.md](../round15-jit.md) (design, rules, tests, mutants, every table); the copy-and-patch question: [docs/perf-design/copy-and-patch.md](../copy-and-patch.md).

* **Why the study's regions covered half of what ran in them:** "ran in regions" counts the escapes (a load or store inside a region is a call of the tier's handler); the generated share is bounded by the opcode set, not by the region extents. What the regions cost was the call (33.6 M of them in SYRK, about 5 instructions each) and an escape 2.6 ns dearer than in the tier's loop.
* **What changed:** a region is now a run of ops the run loop goes on past (uniform branches, S2R and the uniform datapath, stores), cut into stretches; the generated code runs stretch after stretch, loops included, with exact counters, the 256-op run bound, the step budget, the turn's call budget, the chain's conditions and the store gate, and leaves with nothing of the next op done wherever the loop would not go on. Ten more forms are computed (SEL, PLOP3, S2R, CS2R of SRZ, UMOV, ULDC, UIADD3, ULOP3, USEL, UISETP). The run loop of tier 2 goes on past branches itself, issues plain runs back to back, reads only the compiled regions' entries, and escapes call the handler directly.
* **Results (one thread, warm cache, 5 interleaved runs, server3):** tier / JIT **geometric mean 1.099 over the 22 programs of the JIT study** (goal 1.15 not met; the study's JIT: 1.034; corpus 664 s -> 628 s, 1.057x), the 18 programs that have regions 1.122 (simpleHyperQ 1.70, reduction 1.25, LU 1.18, FDTD-2D 1.17, transpose 1.17, SYR2K 1.14, SYRK 1.13 against 0.88), the 4 that have none 1.001; worst 0.982 (fpdc-cuda, spreads of 34 % and 21 %), none more than 2 % slower; A/A control over 15 programs 0.987 to 1.011. The generated code computes 55 % of the 18.1 G instructions (the study: 28 %). Cold (first run, compile on the launching thread): 1.22x of the tier (base JIT 1.14x), all of it the compile (2.3 s a unit, 67 units).
* **Same bits:** results, counters and `VGPU_KERNEL_DIGEST` equal to the tier-only run and to `origin/main` on every program at one thread, cold and warm cache, and at four threads, except the programs whose tier-only run differs from itself at that thread count (radixSortThrust at one and four threads, jacobiCudaGraphs and segmentationTreeThrust at four: the tier-only runs of `origin/main` differ from themselves there, controls in the write-up).
* **Tests (CI-wired, `docs/ci.md`):** `test_jit_resid` (graph regions against a model of the run loop, with and without residence), `test_jit`, `test_sass_{chain_cont,store_gate,alu_runs}_jit`, the new `e2e_sass_jit_shard_loops` (`jit_loops.cu`) and the existing shards; mutation switches (`VGPU_JIT_MUTANTS=ON`) for every rule of the control flow and every new form.
* **Costs and limits:** the compile of a cold unit is 2 to 4 times what it was (larger regions: SYRK 1.1 s -> 4.6 s on this machine); the cheaper form (`VGPU_JIT_RESIDENCE=0 VGPU_JIT_SPECIALIZE=0`: rows in the register file, one body per region) compiled 22 to 48 % faster with no run-time loss, and **became the default in round sp38** (the knobs turn the full form back on: `VGPU_JIT_RESIDENCE=1`, `VGPU_JIT_SPECIALIZE=1`; the matrix was re-run, see "Round sp38 (follow-ups)"). The JIT still computes nothing of memory, shared memory and atomics: they are 30 to 40 % of the time of these programs, which is what stops the geometric mean where it stops.

## Round sp27 (tensor2): IMMA through VNNI, an AVX2 form, 16-byte batches, h_imma's stack frame (branch `sp27-tensor2`, base `sp26-tensor` 59ec7f1b = PR #510)

Question: the sp26 leftovers on `immaTensorCoreGemm` (`imma_frag_m16n8`'s units loop, `load_batch` per 16-byte load, `step_warp`) and `cudaTensorCoreGemm` (the HMMA kernel), and an AVX2 route for hosts without AVX-512. Same host and method as sp26 (server3, Zen 4, Release/LTO, `nvidia/rtx3060`, SASS, one thread, cpu 13, `perf stat -e instructions:u,cycles:u`, 15 alternating runs, 3 library copies a side, A/A control from three more copies of the base). Counters (`VGPU_COUNTERS=1`) and the kernel digests (`VGPU_KERNEL_DIGEST`, 4 threads) of both programs are identical to the base's, at the default level.

### Where the time went (sp26-tensor, immaTensorCoreGemm, `perf record`)
`h_imma` itself was 11 to 21 % of the cycles for a function that only calls the kernel: its frame was 17 KB, because the general path (int32 tiles `ia`, `ib`, ...) lives in the same function, so every call paid three stack probes (`sub $0x1000,%rsp; orq $0,(%rsp)`), a division for the register counts, and the arrays' setup. The kernel `imma_frag_m16n8` was 1,047 instructions and 196 cycles a call at K = 16 (1,670 and 350 at K = 32; a microbenchmark of one call on cpu 13): the sums were a runtime-K loop of `vpmaddwd` pairs, and staging loops with runtime trip counts.

### Changes (results, counters and error text unchanged)
1. **h_imma without the general frame** (`src/sass/tier_ops.inc`): the tile path moved to `imma_tiles`, a `noinline` function; `h_imma` is the fast form and a call.
2. **One call for a warp's 16-byte loads** (`MemoryManager::load_batch16`, `src/core/memory.cpp`; `tier_global16`): one lookup and one pass over the lanes for the two relaxed 8-byte halves (the two `load_batch` calls of sp26 made two of each). It declines what those two calls could treat differently, and then they run as before: a lane not 8-byte aligned, 16 bytes not wholly inside the first lane's allocation, a 16-byte access across the end of a chunk (its halves are in two chunks), a host mapping in the allocation's range, a fault armed, more than 64 lanes. A lane that is to be declined is still read safely (a lane across a chunk end reads at offset 0 of its chunk instead: found by ASan, the first version read its second word past the chunk).
3. **IMMA through `vpdpbusd`** (AVX-512 VNNI, which the Avx512 level has; `imma_frag_k<SA, SB, K>` in `include/vgpu/exec/imma_frag.hpp`, `imma_frag_m16n8` is the dispatch on K): the instruction takes one operand unsigned and one signed, so the four sign combinations are made to fit, exactly, in a sum that is modulo 2^32: A unsigned and B signed: `dpbusd(A, B)`; A signed and B unsigned: `dpbusd(B, A)`; both signed: A's bytes flipped (A + 128 unsigned), `dpbusd(A ^ 0x80, B)` minus 128 x the column sums of B; both unsigned: A flipped (A - 128 signed), `dpbusd(B, A ^ 0x80)` plus 128 x the column sums of B. The column sums are `dpbusd` against ones on the B side that is already staged (two chains), shifted by 7. No widening of the operands. K is a template constant, so the staging loops and the eight units' sums unroll (a runtime K left them as loops of 12 instructions an iteration): 8 independent accumulators, one load of the B side per four bytes of K for all eight units. B is staged by one two-source permute per dword of K.
4. **IMMA at the AVX2 level** (`imma_frag_avx2_k`, same file): 16-bit widening and `vpmaddwd` for a unit of one row by 8 columns, used for `Level::Avx2` (a host without AVX-512, or `VGPU_SIMD=avx2`). Before, AVX2 hosts took the general tile path.

### Caveats and what is left
* The base is sp26-tensor (PR #510); against `origin/main` the sp26 gains come first (cudaTensorCoreGemm 0.63x cycles, immaTensorCoreGemm 0.30x).
* An AVX2 route for HMMA fragments was not written: at `VGPU_SIMD=avx2` cudaTensorCoreGemm is 57 % `mma_avx2_chunked_f`'s units, 13 % its operand decode and 8 % `hmma_k`'s preparation, and the preparation is conversions and transposes the kernel needs in row-major form anyway; a fragment-fed form would save the one intermediate pass (`FA`/`FB`), estimated under 1 %.
* Left in the immaTensorCoreGemm profile (cycles): `step_warp` 22 % (the tier loop inlined: barriers, group pick, program counter refresh), `imma_frag_k` 20 %, `h_global` 12 %, `load_batch16` 11 % (cache misses of the gather: waiting, not work), `h_imma` 10 % (the four result stores), `h_ldsm` 5 %, `random` 6 % (the sample's own initialisation).
* A 16-byte access across a chunk end needs an address that is 8-byte but not 16-byte aligned; a card faults on that, so the declined path is the safety net and no real program takes it.
* Layout: `lint_hot_unit_layout` passes (the AVX2 form is `aligned(64)`; the first version at 32 bytes failed it).
